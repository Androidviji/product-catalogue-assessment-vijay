## Stage 1: backend foundation

Decisions made during the build, with evidence:

- **Spring Boot 4.1.2.** Spring Initializr (checked live) only offered 4.x versions, so the AI used
  the current stable release. The project skeleton and Maven wrapper were generated by Initializr
  rather than written from memory, because Boot 4 changed starter names (`spring-boot-starter-webmvc`)
  and test packages (`org.springframework.boot.webmvc.test.autoconfigure`).
- **Fetch the full product list once, not one request per featured ID.** A live check showed Fake Store
  returns `HTTP 200` with an empty body for an unknown ID (`/products/999`), not a 404. Fetching the list
  (20 products) and looking IDs up locally makes "missing" unambiguous and needs one call instead of five.
- **Missing featured product policy.** Return the found products in configured order, list the missing
  IDs in `missingProductIds`, include `configuredCount`, and log a warning. The response never implies
  that all five were found.
- **Configuration is checked at startup.** An empty or duplicated `featured-product-ids` list stops
  the app from starting, so the mistake is caught before customers see it.
- **Three product shapes on purpose:** Fake Store JSON (private to `FakeStoreProductSource`) maps to our
  `Product`, which maps to `ProductResponse` (the API contract). `Product` keeps the source image URL
  internally for the later image endpoint; `ProductResponse` does not expose it.
- **Timeouts:** 3s connect, 5s read, configured on the JDK `HttpClient` request factory. There is a test that
  proves a server that never replies produces a 503-style failure in under 3 seconds.
- **Errors:** a 503 RFC 9457 problem response with `code: PRODUCT_SOURCE_UNAVAILABLE`. The full exception
  is logged on the server only. A test checks that the response body does not contain the internal message.
- **Mailpit pinned to `v1.33.1`**, not `latest` or the two-day-old `v1.34.0`. Ports are bound to `127.0.0.1`.
- **Left out for now:** the validation starter (no request input yet), caching of the product list,
  and category or search endpoints.

Issues hit (environment, not AI errors):

- In Claude Code's PowerShell sandbox, `mvnw.cmd` could not resolve `repo.maven.apache.org`, so
  tests were run with `./mvnw` from Git Bash instead. This does not affect a normal PowerShell window.

AI mistakes caught in this stage: none yet.

## Stage 2: remaining backend features

- **Prompt (summary):** implement the remaining backend features only: categories with top three by
  rating plus the rest, search, product details, an image endpoint by product ID, and an enquiry endpoint
  that emails a configured sales inbox over SMTP (Mailpit locally). Keep the email sender behind an
  interface. Add focused tests, run the real checks, update the README and these notes, and do not commit.
  Inspect stage 1 first and preserve it.

Decisions made during the build, with evidence:

- **Checked the live data before choosing a tie-breaker.** Fake Store's `electronics` has two products
  rated 4.8 (IDs 11 and 12), so a tie-breaker changes the real result. The order is rating desc, then rating
  count desc, then ID asc. The whole category is sorted once and split after three products, so the
  "top three" and "others" groups cannot overlap.
- **Categories are derived from the product list,** not from Fake Store's categories endpoint. One source
  of truth means a listed category is never empty. Unknown categories return 404 `CATEGORY_NOT_FOUND`.
- **Blank search returns 400** `INVALID_SEARCH_QUERY` instead of "all products" or an empty list, so the
  app can show a clear message. No matches returns 200 with an empty list.
- **Image endpoint:** a separate one-method `ProductImageSource` interface, implemented by
  `FakeStoreProductSource` so Fake Store knowledge stays in one class. Restrictions: same scheme, host and
  port as the configured base URL, no redirects (JDK HttpClient default; covered by a test with a real
  local HTTP server), png/jpeg/gif/webp only (SVG refused), 5 MB cap. Live check: the image for product 1
  is `image/png`, 273,291 bytes. A missing image on Fake Store returns 404 with `text/html`.
- **`ApiExceptionHandler` now extends `ResponseEntityExceptionHandler`** (a stage 1 change), so
  validation errors can list each invalid field. The AI first checked, by inspecting the Boot 4.1.2 class
  with `javap`, that Boot's own problem-details handler is `@ConditionalOnMissingBean(ResponseEntityExceptionHandler)`.
  Framework errors therefore keep the problem-details shape, and there are no competing handlers.
- **Enquiry success means the SMTP server accepted the message:** `JavaMailSender.send` returns only after
  the server accepts it. Failures become `EmailDeliveryException`, then 503 `EMAIL_SEND_FAILED` with a
  generic message. Logs record only the enquiry UUID, the product ID and the root-cause type and message. A
  test captures log output and asserts the customer's name, email and message are absent.
- **Product details in the email come from the product source,** not from the request.
- `customerName` rejects control characters (line breaks), because it is copied into the email body.

## Stage 2 review fixes

- **Review finding:** `EnquiryService` logged the root SMTP exception's message on send failure, which
  could contain customer email addresses. The AI introduced this in stage 2, and the stage 2 notes above
  record that version ("root-cause type and message"). It now logs only the enquiry ID, the product ID and
  the exception type. The test uses a provider error that echoes the customer's address and an SMTP user
  name, and asserts that neither reaches the log.
- **Review finding:** the README said every error has a `code`, but framework errors (malformed JSON,
  wrong path-variable type, unknown URL, wrong method) had none. Malformed JSON and type mismatches now get
  specific codes with safe text that does not echo the value (`MALFORMED_REQUEST`, `INVALID_PARAMETER`).
  Other framework errors get their HTTP status name as the code, and unexpected exceptions get a generic
  500 `INTERNAL_ERROR`.
- **AI mistake caught by tests:** the first version added the fallback code to the `body` passed into
  `handleExceptionInternal`. For most framework errors, Spring passes `null` there and builds the problem
  detail inside `super`, so 404, 405 and 415 still had no code (3 test failures). Fixed by adding the code to
  the response returned by `super`.
- A new test first treated the rejected value appearing in `instance` (the request path) as a leak. That
  is the client's own URL, so the test now checks `detail` instead.

## Stage 3 review fix: ambiguous enquiry failures

- **Review finding (from the developer):** the enquiry screen said "Your enquiry was not sent" for every
  failure and suggested retrying. After a timeout or a lost connection, the backend may already have
  sent the email, so that message could be wrong, and a retry could create a duplicate.
- **Change:**
  - `safeApiCall` now separates `NoConnection` (never connected: unknown host, connection refused,
    no route) from a new `ConnectionLost` (the connection broke after connecting).
  - `SubmitEnquiryResult` gained `Unconfirmed`. `EnquiryRepositoryImpl` returns `Failed` only when
    "not sent" is certain: no connection, any 4xx, or 503 `EMAIL_SEND_FAILED` /
    `PRODUCT_SOURCE_UNAVAILABLE`. A timeout, `ConnectionLost`, an unreadable 200 or any other 5xx
    returns `Unconfirmed`.
  - The enquiry screen shows "We couldn't confirm your enquiry … may receive it twice", keeps the
    fields, and labels the button "Send again".
  - On the catalogue screens, `ConnectionLost` shows the same text as `NoConnection`.
- **Decision:** a 503 without a known code, or a 502/504 from a proxy, is treated as unconfirmed rather
  than "not sent". A gateway can time out while the backend is still sending the email.
- **Checked, not assumed:** a test sends the enquiry to a server that drops the connection after
  receiving the request. It asserts the server saw exactly one request, because OkHttp can retry
  automatically on connection failures. It passed (1 request). Other failure modes were not tested for
  automatic retries.
- **Not implemented, documented as a future improvement:** an idempotency key sent with each enquiry
  attempt, so the backend can ignore duplicates.
- Result: `gradlew testDebugUnitTest`: 49 tests, 0 failures (8 new). The unconfirmed message was not
  reproduced on the emulator.

## Stage 3 review fix 2: conservative enquiry outcomes and OkHttp retries

- **Review finding (from the developer):** `EMAIL_SEND_FAILED` does not prove that SMTP rejected the
  message (the server may accept it before the backend misses the final acknowledgement), and a 4xx
  does not prove the backend did not process the enquiry (a proxy may have generated it). The developer
  also asked for a review of OkHttp's automatic retries for the enquiry POST.
- **AI mistakes corrected:** both were the AI's choices in the previous fix.
  - It had classified `EMAIL_SEND_FAILED` and every 4xx as "definitely not sent".
  - Its earlier "POST reached the server exactly once" test only covered a fresh connection. That
    happens not to retry, so it did not show retries were impossible in general.
- **Evidence gathered:**
  - Read `RetryAndFollowUpInterceptor`, `ExchangeFinder` and `OkHttpClient` from the OkHttp 4.12.0
    sources jar on Maven Central (the version the build resolves). An `IOException` after the request
    may have been sent is recovered when `retryOnConnectionFailure` is true, the body is not one-shot,
    the error is not a `ProtocolException` or timeout, and `retryAfterFailure()` allows another
    attempt. That includes a call made on a reused pooled connection.
  - A new test reproduced this with the default client: the same POST was sent twice (3 requests).
  - Run against the app as it was before this fix, the new enquiry test failed:
    `expected Unconfirmed(ConnectionLost) but was Sent(should-not-be-used)`. The app had silently
    resent the enquiry.
- **Changes:**
  - `AppContainer`: enquiries use `okHttpClient.newBuilder().retryOnConnectionFailure(false)`
    through their own Retrofit instance. GETs keep automatic retries. A test covers each.
  - `EnquiryRepositoryImpl`: "not sent" is now limited to two cases. First, never connected
    (unknown host, refused, no route), which is valid only because retries are off. Second, our
    backend's codes that occur before sending: `MALFORMED_REQUEST`, `UNSUPPORTED_MEDIA_TYPE`,
    `PRODUCT_NOT_FOUND` and `PRODUCT_SOURCE_UNAVAILABLE`. That ordering was confirmed in
    `EnquiryController` (`@Valid`) and `EnquiryService.submit` (product lookup at line 39, send at
    line 50). Everything else is `Unconfirmed`, including `EMAIL_SEND_FAILED` and any bare 4xx/5xx.
  - The unconfirmed message no longer claims "the connection was interrupted", since it now also
    covers server responses.
- **Remaining uncertainty (documented in README):**
  - Retries by a proxy or load balancer in front of the backend.
  - The customer choosing Send again.
  - Connect timeouts are treated as unconfirmed even though nothing was sent.
  - Many `EMAIL_SEND_FAILED` cases are real failures but cannot be told apart without a backend change.
  - The idempotency key is still only a documented future improvement.
- Result: `gradlew testDebugUnitTest`: 54 tests, 0 failures. `assembleDebug` and `lintDebug`
  succeeded. Not checked on the emulator, which had been stopped earlier because the computer was low
  on memory.
